# Using the library

`@nicolassancho/storybook-core` is a set of accessible React components styled with Tailwind CSS v4.
This page covers what an app needs to consume it, with examples for the Next.js App Router.

## Install

The package is public on npm, so no registry or token setup is needed:

```bash
npm install @nicolassancho/storybook-core
```

The library expects these peer dependencies in the app: `react` and `react-dom` (19), `tailwindcss` (v4), `tailwind-variants` (v3) and `tailwind-merge` (v3).

```bash
npm install tailwindcss tailwind-variants tailwind-merge
```

## Set up the styles

The library ships its design tokens, not compiled CSS. Import the tokens and tell Tailwind to scan the
library's compiled files for classes:

```css
/* app/globals.css */
@import "tailwindcss";
@import "@nicolassancho/storybook-core/styles/theme.css";
@source "../node_modules/@nicolassancho/storybook-core/dist";
```

The `@source` line is required. Tailwind skips `node_modules` when it looks for classes, so without it
the components render unstyled. Adjust the relative path to where your CSS file lives.

## Fonts

The library loads no fonts. Components use `font-sans` for body text, and `Text` takes
`font="display"` for headings, which uses `font-display`. Set both once in your app: with
`next/font` the fonts are self-hosted and cause no layout shift.

```tsx
// app/layout.tsx
import { Bricolage_Grotesque, Hanken_Grotesk } from "next/font/google";

const body = Hanken_Grotesk({ subsets: ["latin"], variable: "--font-body" });
const heading = Bricolage_Grotesque({ subsets: ["latin"], variable: "--font-heading" });

<html className={`${body.variable} ${heading.variable}`}>
  <body className="font-sans">{children}</body>
</html>;
```

```css
/* app/globals.css, after the library import */
@theme inline {
  --font-sans: var(--font-body), ui-sans-serif, system-ui, sans-serif;
  --font-display: var(--font-heading), ui-sans-serif, system-ui, sans-serif;
}
```

`--font-display` is optional: when you do not set it, headings use the body font. The type scale
sets a line-height for each size, and its sizes are in rem.

## Dark mode

`theme.css` also holds the dark theme. With no setup it follows the operating system
(`prefers-color-scheme`). To let the user choose, set `data-theme="light"` or `data-theme="dark"` on
`<html>`; the attribute wins over the OS setting. The color names do not change (`neutral-900` is still
body text, `primary` is still the brand blue), only their values, so the components need no props and
your own classes switch with them.

**The theme is page-wide.** Set `data-theme` on `<html>` only. Tailwind compiles each `light-dark()`
token into a toggle that is resolved at the root, so a `data-theme` on a nested element changes
nothing. You cannot, for example, show a dark card inside a light page.

Two things are on your side:

- Give the page its colors, since the components inherit the text color and sit on your background:

```tsx
// app/layout.tsx
<body className="bg-surface text-neutral-900">{children}</body>
```

- Use the token pairs in your own markup. `bg-surface` is the default background, and a filled brand
  background pairs with its `on-` color (`bg-primary text-on-primary`, also `on-secondary` and
  `on-danger`). Do not use `bg-white` or `text-white` for these: they stay white in dark mode.

For a toggle that remembers the choice and does not flash on load, `next-themes` works with the
attribute (the provider is a client component in your app):

```tsx
// app/providers.tsx
"use client";

import { ThemeProvider } from "next-themes";

export function Providers({ children }: { children: React.ReactNode }) {
  return (
    <ThemeProvider attribute="data-theme" defaultTheme="system" enableSystem>
      {children}
    </ThemeProvider>
  );
}
```

Add `suppressHydrationWarning` to `<html>`, because the attribute is set before React hydrates. To
write `dark:` variants in your own classes, tell Tailwind to use the same attribute:
`@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *));`. That variant matches
only the attribute, so it does not follow the OS when `data-theme` is not set (`next-themes` always
sets it).

The Storybook toolbar has a theme switch (Light, Dark, System) so you can see every component in
both themes. `npm test` runs every story in both, with the axe checks.

## Quick start

Import components from the package root. Unused components are dropped from your bundle.

```tsx
import { Button, Text } from "@nicolassancho/storybook-core";

export default function Page() {
  return (
    <>
      <Text as="h1" size="large" weight="bold">
        Hello
      </Text>
      <Button>Shop now</Button>
    </>
  );
}
```

## Links and images

Anything that navigates takes an `href`, and renders a plain `<a>` by default. Anything that shows an
image renders a plain `<img>` by default. To use your framework's components, pass them in:

```tsx
import Image from "next/image";
import Link from "next/link";
import { Breadcrumbs, ProductGrid } from "@nicolassancho/storybook-core";

export default function Page() {
  return (
    <>
      <Breadcrumbs
        LinkComponent={Link}
        items={[
          { label: "Home", href: "/" },
          { label: "Shirts", href: "/shirts" },
          { label: "Basic T-Shirt" },
        ]}
      />
      <ProductGrid
        LinkComponent={Link}
        ImageComponent={Image}
        products={[
          {
            id: "basic-t-shirt",
            title: "Basic T-Shirt",
            brand: "Acme",
            price: "$19.99",
            href: "/products/basic-t-shirt",
            imageUrl: "/basic-t-shirt.jpg",
            imageProps: { width: 300, height: 400, sizes: "25vw" },
          },
        ]}
      />
    </>
  );
}
```

- `LinkComponent` receives `href`, `className` and `children` (and `aria-current` on `ChipLink`, which
  `next/link` forwards). `ButtonLink` takes the same `LinkComponent`. `ImageComponent` receives `src`,
  `alt`, `className` and the attributes in `imageProps`.
- A product card with an `href` is a real link stretched over the whole card, so middle-click, new tab
  and crawlable URLs work. Its image is decorative (`alt=""`), because the title names the card. Without
  an `href` the card is display-only.
- Controls go in the card's `actions` prop, for example an add-to-cart `<form>`. They sit above the
  stretched link, so pressing one does its own action and pressing anywhere else opens the product:

```tsx
<ProductCard
  title="Basic T-Shirt"
  href="/products/basic-t-shirt"
  actions={
    <form action={addToCart}>
      <Button type="submit">Add to cart</Button>
    </form>
  }
  // ...brand, price and imageUrl
/>
```

- `ProductGrid` forwards its `LinkComponent` and `ImageComponent` to every card. A product can bring
  its own.
- Pass the imported component directly, or define your own outside the render function. A component
  defined inline is a new component on every render, so React remounts it and the links lose their
  state.

```tsx
// Remounts on every render:
const Bad = () => <Breadcrumbs LinkComponent={(props) => <Link {...props} />} items={items} />;

// Stable:
const Good = () => <Breadcrumbs LinkComponent={Link} items={items} />;
```

### Typed routes

With `typedRoutes: true` in `next.config`, Next types `Link`'s `href` as a known route. The library passes the
`href` string you gave it, so `LinkComponent={Link}` fails the type check with "is not assignable to type
ElementType". Wrap `Link` once and pass the wrapper. The hrefs are your own props, so the cast hides nothing
the compiler could have checked:

```tsx
// components/nav-link.tsx
import Link from "next/link";
import type { ComponentProps } from "react";

type Href = ComponentProps<typeof Link>["href"];

export const NavLink = ({
  href,
  ...props
}: Omit<ComponentProps<typeof Link>, "href"> & { href: string }) => (
  <Link href={href as Href} {...props} />
);

// <ButtonLink href="/products" LinkComponent={NavLink}>Products</ButtonLink>
```

The wrapper is a Server Component, so it adds no client JavaScript.

## Page width

`Header` and `Footer` keep their bar full-width and put their content in a `Container`: centered, at
most 72rem wide, with side padding. Wrap your page content in a `Container` to line it up with both:

```tsx
import { Container } from "@nicolassancho/storybook-core";

export default function Page() {
  return (
    <Container as="main" className="py-12">
      {/* page content */}
    </Container>
  );
}
```

Use `className` for spacing. The width and the side padding belong to the design system, so that the
header, the page and the footer cannot drift apart.

## Next.js App Router

Presentational components hold no state and use no browser APIs, so they carry no `"use client"` directive
and render from Server Components. Components that need interaction (a menu or a dialog, for example) are
client components: each carries `"use client"` in its own file and says so in its documentation. You import
both kinds the same way from a Server Component. A client component is a small island of client JavaScript in
an otherwise server-rendered page, and a Server Component cannot pass it functions such as event handlers
(pass data, or wrap it in your own `"use client"` file). Static usage needs nothing special: the examples
above are Server Components. `Header` takes its brand, actions and navigation as props, so it works there
too:

```tsx
<Header
  brand={<Link href="/">Shop</Link>}
  actions={<SearchForm />}
  navItems={[{ label: "Ceramics", href: "/products?category=ceramics" }]}
  LinkComponent={Link}
/>
```

An event handler (`onClick`, `onChange`) is a function, and Next cannot pass a function from a Server
Component. Keep the interactive part in a small Client Component in your app, and render it from the
server page:

```tsx
// app/search-bar.tsx
"use client";

import { useState } from "react";
import { Button, Input, Text } from "@nicolassancho/storybook-core";

export function SearchBar() {
  const [query, setQuery] = useState("");
  const [submitted, setSubmitted] = useState("");

  return (
    <>
      <Input
        type="search"
        label="Search"
        hideLabel
        value={query}
        onChange={(event) => setQuery(event.target.value)}
      />
      <Button onClick={() => setSubmitted(query)}>Search</Button>
      {submitted && <Text>Searching for {submitted}</Text>}
    </>
  );
}
```

Prefer a real link over a handler when the action is navigation: a link needs no JavaScript.

## Forms and filters without JavaScript

`RadioGroup` and `Input` also work uncontrolled: leave out `value` and `onChange`, and set the
starting state with `defaultValue`. They then render from a Server Component inside a native `<form>`,
and the browser submits what the user chose. Pick one mode per component and keep it: React warns when
an input switches between controlled and uncontrolled.

`ChipLink` is a pill link for a category or filter that lives in the URL, and `selected` sets
`aria-current="true"` on it. `Chip` is the button version: `selected` sets `aria-pressed`, and a
`type="submit"` chip with a `name` and `value` submits a form, so it needs no handler either.

`ButtonLink` is a link that looks like a `Button`, for a call to action that goes to another page.
Use `Button` for an action that runs code or submits a form. A link cannot be disabled, so
`ButtonLink` has no `disabled` prop.

```tsx
// app/products/page.tsx (a Server Component)
import Link from "next/link";
import { Button, ChipLink, Input, RadioGroup } from "@nicolassancho/storybook-core";
import { addToCart } from "./actions";

export default function Page() {
  return (
    <>
      <nav aria-label="Categories">
        <ChipLink href="/products" LinkComponent={Link} selected>
          All
        </ChipLink>
        <ChipLink href="/products?category=shirts" LinkComponent={Link}>
          Shirts
        </ChipLink>
      </nav>

      {/* A GET form: the query lands in the URL, and the page reads it on the server. */}
      <form action="/products">
        <Input type="search" label="Search" hideLabel name="q" defaultValue="shirt" />
        <Button type="submit">Search</Button>
      </form>

      {/* A Server Action receives the chosen option as a string. */}
      <form action={addToCart}>
        <RadioGroup
          label="Color"
          name="color"
          defaultValue="blue"
          options={[
            { label: "Blue", value: "blue" },
            { label: "Red", value: "red" },
          ]}
        />
        <Button type="submit">Add to cart</Button>
      </form>
    </>
  );
}
```

`Input` is a text field with its label, optional help text and optional error. The label, description and
error are linked with native attributes (`for`, `aria-describedby`, `aria-invalid`), so it needs no
JavaScript. Pass the error from the Server Action result. Focusing the field after a failed submit is the
page's job.

Use the controlled form (`value` and `onChange`) only when the page needs the live value, and keep it in
a Client Component as shown above.

## Menus and drawers with `Popover`

`Popover` is a button that opens a panel, for a user menu, a dropdown or a navigation drawer. It is the
library's first client component, and you still render it from a Server Component without writing any client
code:

```tsx
// app/(app)/layout.tsx (a Server Component)
import Link from "next/link";
import { Button, Popover } from "@nicolassancho/storybook-core";
import { signOut } from "./actions";

<Popover trigger="Ana Ruiz" placement="bottom-end">
  <Link href="/settings">Settings</Link>
  <form action={signOut}>
    <Button type="submit" variant="outline">
      Sign out
    </Button>
  </form>
</Popover>;
```

It uses the browser's native `popover`, so the browser closes it on an outside click and on Esc, returns focus
to the button and draws it above the page. The component adds `aria-expanded` on the button, closes the panel
when a link inside it is clicked or a form inside it is submitted (so `next/link` and Server Actions work with
no router code), and places a dropdown under its button. The panel content stays a Server Component. Every prop
must be serializable: pass text and elements, not functions. Without JavaScript the panel still opens and
closes through the native attributes; only the closing on a link click and `aria-expanded` need it.

`placement="drawer"` opens a full-height panel from the left edge, with a close button at the top
(`closeLabel` sets its accessible name, "Close menu" by default). It is not modal: keyboard focus can still
move to the page behind it. Put a `SidebarNav` inside it for a navigation drawer. `SidebarNav` stays a Server
Component, so it is not added to the client bundle. It cannot know the URL, so pass `current: true` on the
item for the page the user is on, which an app usually derives with `usePathname` in a small Client Component.

## What the package exposes

- `@nicolassancho/storybook-core`: every component and its types.
- `@nicolassancho/storybook-core/styles/theme.css`: the design tokens.

Other paths, such as files inside `dist/`, are not part of the public API. The package is ESM only. It
works in bundlers (Next.js, Vite, webpack) and in Node's native ESM loader.

## Accessibility

- Give inputs an accessible name: `Input` requires a `label` (visible, or hidden with `hideLabel`),
  which names the field for screen readers.
- Icons are decorative by default. Pass `ariaLabel` when an icon carries meaning on its own.
- Use `alt=""` for purely decorative images, and a real description otherwise.
